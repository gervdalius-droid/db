## The product refuses to sell itself while it is unsafe

`fabsuite/readiness.js` runs on the storefront and the signup page. Before it
lets anyone reach checkout it asks the live API, using nothing but the
publishable key that ships in the page, whether tenant rows come back — and it
checks that Terms and Privacy name a real seller. If either fails, every route
into checkout is removed and visitors see an honest "sign-up is paused" notice
with your address on it.

It blocks only on **positive evidence** of a problem. A timeout, an unreachable
API or an unreadable answer leaves the page working — a hiccup must never take
the storefront down. `?readiness=1` on any storefront page prints the diagnosis.

Right now, against the live project, it reports:

```
tenant isolation (migration 0005)  OK — the publishable key is refused
legal identity (LEGAL in config)   OK
checkout                           live (Stripe)
```

**Sign-up is open.** All five plan CTAs are live and the gate is satisfied.

That file is generated by `python3 scripts/apply-migrations.py --print` and is
verified end to end: `scripts/rls-test/run.sh` applies **that exact file**, as a
single transaction, to a database in the same state as yours — then proves two
tenants stay isolated, workers keep access, and re-running it is harmless.

## 🟢 Done and verified

Two suites cover this, both exiting non-zero on failure:
`scripts/suite-test/run.sh` (55 checks — the apps and the built product) and
`scripts/rls-test/run.sh` (25 checks — the migrations, on a real Postgres).

**Four apps, one workspace, one gate**
- CRM (new), Offer (productised), Nesting, DB — all gated by
  `FabsuiteLicense`, all reading the generic `apps` entitlement list.

**They are actually joined up**

```
CRM ──won deal──► Offer ──accepted quote──► DB ──cut list──► Nesting
 └────────────────── won deal ─────────────►┘
```
- Every hop carries the client, project name and value on the query string; the
  DB app pre-fills its new-project modal and strips the query so a refresh
  cannot duplicate the project. A project created this way keeps `crmDealId`.

**Saving and backup, identical in every app**
- `shared/craftos-backup.js`: dated JSON snapshot, restore with a confirmation
  that names what is being replaced, and a once-a-day nudge. Same envelope
  everywhere (`{craftos_backup, app, workspace, exportedAt, data}`), so the DB
  app's restore reads the others' files too.
- CRM saves on every change (debounced, with a localStorage mirror); Nesting and
  Offer back up **every project in the workspace**, not just the open one; the DB
  app keeps its xlsx backup with the embedded snapshot sheet.

**Multi-tenancy bugs found and fixed**
- `fabflow_projects` had **no workspace column** — two customers saving "Virtuvė"
  overwrote each other, and every project list showed every customer's projects.
  Fixed in code and in migration 0004.
- Nesting sent the **anon key** for every project read and write; under RLS that
  reads nothing, and without RLS it is everyone's data. Now sends the user token.
- Nesting's localStorage mirror was unscoped; signing a second company into the
  same browser showed the first company's projects. Now scoped, with a one-time
  adoption of legacy keys.
- `set-worker-pin` created workers with no `org_members` row — RLS would have
  locked out every worker on day one. Now kept in lockstep.

**Localisation**
- All four apps in LT/EN/DE/ES, sharing the `fab_lang` key so the choice carries
  across them. The Offer app's 221 inline language ternaries were converted to
  dictionary keys and all 513 keys translated; dropdown labels translate while
  the stored values stay canonical. CRM demo data is localised too.

**Commerce**
- Five plans (CRM/Offer €29·290, Nesting €39·390, DB €49·490, suite €89·890),
  trial length driven by config, Terms + Privacy (incl. an Art. 28 processing
  agreement) in EN and LT.
